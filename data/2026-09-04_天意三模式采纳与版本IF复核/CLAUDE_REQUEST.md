### 1. 产品定位、作者与 AI 权限边界

来源：`TIANYAN_PRODUCT_CORE.md`「一、项目」「三、完整产品的层次」「四、作者与 AI 的基本关系」「五、故事信息的基本层次」。

> 天衍是一个故事世界创造与演化系统。
>
> 它帮助拥有想法但不一定拥有成熟写作能力的人，把零散、模糊、跳跃的想法逐步发展为结构清楚、长期一致、可继续演化的故事世界，并把这些故事安全地交给不同外部工具继续制作。
>
> 天衍不是普通 AI 写作软件，也不是只会生成正文的聊天机器人。它的核心不是“替作者写完”，而是：理解、整理、记忆、模拟、协作、保护、延展和连接。
>
> 作者控制宏观方向、价值判断和最终决定。AI 负责理解、整理、记忆、推理、模拟、发现问题和执行受控工作。

> 天衍不是让 AI 偷偷修改正式故事的自动驾驶系统。AI 可以分析、建议、生成候选、在派生副本中自主推演，也可以在作者明确授权后执行编辑；但作者始终拥有正式故事的最终决定权。

作者拥有：

- 故事方向的决定权；
- 角色、事件、关系、规则和设定的最终确认权；
- 原始主线是否修改的决定权；
- 派生副本是否同步、保留、融入或删除的决定权；
- Agent 是否采纳、分类、修改或删除的决定权；
- 哪些内容可交给外部插件的决定权；
- 历史版本、外部输出和插件使用的控制权。

AI 负责：

- 听懂作者的模糊想法；
- 主动询问和澄清；
- 整理人物、地点、物品、组织和自定义对象；
- 提炼节点、集点、单元、主线、支线、暗线和伏笔；
- 维护关系、记忆、知识边界和世界状态；
- 提出候选和影响分析；
- 进行局部预测；
- 在作者授权的派生副本中持续演化；
- 帮助选择和调用外部工具；
- 保留来源、历史、回执和解释。

权限不是只有“允许”与“不允许”：

- **只读**：只能理解和解释，不能产生待写入变化。
- **建议**：可以提出建议，但不生成可直接写入内容。
- **候选**：可以生成候选，等待作者审查。
- **授权编辑**：在作者明确的对象、范围和时间内执行编辑。
- **派生副本自主运行**：AI 可以在副本内根据权限连续推演，不能越界修改原始主线。
- **后台工作**：执行索引、分析、同步检查、质量检测等非正式写入任务。

> 确认不等于每改一个字都弹一次窗口。作者可以对一次操作、一个批次、一个单元或一个派生副本预先给出范围授权；系统仍需保留清楚的修改记录、影响说明和撤销能力。

内容层次：

- 原始来源：用户原文和导入来源必须完整保留，不能被摘要、提炼或 AI 改写覆盖。
- 作者意图：作者明确表达的目标、偏好、限制、排除项和未来方向。
- AI 候选：AI 生成但尚未被作者确认的角色、事件、关系、规则、正文或其他变化。
- 已确认内容：由作者确认或在明确授权范围内写入的资料、事件、关系、规则和设定。
- 派生副本内容：副本内真实有效，但不会自动成为原始主线正式内容。
- 外部输出产物：必须保留来源故事包、工具、版本、参数和回执，不能自动反向成为正式故事。

### 2. 原始主线、历史版本、临时分支、派生副本与待合并变化

来源：`TIANYAN_PRODUCT_CORE.md`「六、核心术语」。

> **原始主线**：当前被作者认可的正式故事版本。它不是永远不变，但任何修改都需要经过明确作者操作、保留历史并可恢复。

> **派生副本**：从原始主线或另一个副本的某个版本完整拎出的一份可独立演化的故事副本。派生副本不是一个单独节点，也不等于临时分支。它拥有自己的内容、历史、Agent、事件线、时间线和后续变化。女娲副本、翻译副本、视角副本、IF 副本和本土化/改编副本都可以采用这一模型。

> 独立故事分支是具有稳定来源、版本身份和独立后续变化的故事方向。在本稿中，它通常由派生副本承载；一次筛选、一次女娲运行、一个预测结果或一组待审修改不会因此自动成为独立故事分支。只有作者明确选择长期保留，并建立来源与版本身份后，它才进入分支和副本管理。

> **临时分支**：原始主线或派生副本内部，为了尝试某种局部可能性而形成的短期分叉。临时分支可以比较、合并、保留、放弃或继续成长为新的派生副本。它比完整副本范围更局部。

> **待合并变化**：女娲、多元、事件预测或其他 AI 工作产生、已经可以对照但尚未写入目标故事的变化集合。它可以包含候选事件、关系变化、Agent 状态变化、世界状态变化和写作建议。它必须绑定来源、目标、运行或候选身份、差异和作者决定，但不因此拥有独立 Canon、Event 或 WorldState。

> **历史版本**：同一原始主线或派生副本在某次重要变化后的不可混淆版本记录。历史版本用于对照、恢复、追溯和解释，不是当前仍在独立发展的故事分支。恢复旧版本应形成可追溯的新操作，不能抹掉后续历史。

> **融入**：作者把派生副本中的内容带回原始主线或另一个目标副本。融入不是简单覆盖。系统需要明确显示来源、目标、来源版本、目标版本、变化范围、冲突、影响、权限、作者确认和回执。融入后形成新的目标版本，旧版本继续保留。

### 3. 天意大页面当前核心表述

来源：`TIANYAN_PRODUCT_CORE.md`「八、天衍的八个空间 → 2. 天意」。

> 天意是整个产品的统一智能入口。
>
> 它负责理解作者、保持长期上下文、管理来源、解释系统、提出候选、安排工作、连接 Agent，并把复杂故事问题转成作者可理解的下一步。

#### 创意模式

> 创意模式适合只有一个想法、想通过聊天逐步把故事说清楚的作者。

它需要支持：持续文字对话、语音对话、暂停与继续、上传文档/图片/音频、拖入左侧工程目录内容、长期会话、自动整理上下文、查看使用了哪些上下文、查看来源、对比原话与提炼结果、逐步形成候选角色/地点/物品/事件/关系/世界规则/写作风格/剧情想法/灵感/创意。

> 创意模式不是“按下录音后让 AI 自己总结”，而是人与 AI 共同把模糊想法逐步发展为可用的故事世界种子。

#### 对话模式

> 对话模式接近 Codex 式精细工作。

它适合：分析已有故事、规划结构、重构、批量整理、写工作蓝本、管理上下文、执行受控编辑、调用 Skills 和 Workflows、检查冲突、处理长任务、查看任务计划和回执。

界面应支持连续对话、文件和来源面板、任务计划、可展开工作步骤、工具调用记录、候选变化、影响范围、错误恢复、停止和继续、历史会话。

#### 天意 UI

> 天意页面必须清楚看到“创意模式 / 对话模式”的切换。模式切换后不丢失当前作品、来源、附件、上下文、任务和历史。中央区域以对话和工作内容为主。输入区根据模式变化：创意模式更强调聊天、语音和上传；对话模式更强调任务、范围、工具和执行控制。

### 4. 页面专属 Agent 模式

来源：`TIANYAN_PRODUCT_CORE.md`「十、天意 Agent 模式」。

> 天意 Agent 模式位于页面右上方或右侧工作区，是“当前页面专属的天意能力”。
>
> 它不是第二个天意，也不是另一套会话 owner。它与天意大页面共享身份、记忆、来源、权限和历史，但在不同页面加载不同的工具、对象和操作模板。

页面示例：

- 世界：统计世界数据、解释日志、汇总待确认、查询版本与派生状态。
- 天意：管理会话、整理上下文、合并候选、控制附件来源、管理长任务。
- 事件线：操作节点/集点/单元、分析因果、预测、检测漏洞、对照副本、预览影响。
- 女娲：设置运行目标和约束、暂停/恢复/分支、查看预算、选择同步和对照范围。
- 多元：术语对齐、知识检查、前提变化影响、同步冲突、派生副本对照。
- 资料：批量整理、提取、分类、查重、关系建议、来源解释和冲突检测。
- 创作：故事包检查、插件选择、格式适配、输出预览和回写审查。

### 5. 事件线预测、候选、采纳与正式写入

来源：`TIANYAN_PRODUCT_CORE.md`「八 → 3. 事件线 → 事件线预测」「完整作者体验 → 体验三」。

> 事件线预测是轻量、直接的作者辅助。

作者可以：选中节点后预测未来；选中连续片段后预测中间缺失；要求多个方向；拖动预测节点；修改或删除；审阅并采纳整条候选路径或部分节点；保留为 IF；提供新想法后重新预测；送入女娲深入推演。

自动边首先是 Candidate，不是正式 Relation。作者部分采纳节点时，只能保留两端都被采纳或引用的边；Candidate ID 到 draft Event ID 或 existing Event ID 的映射必须可恢复、可重放并保持幂等。符合已有 RelationType 的边通过唯一 Relation Owner 进入“待确认关系”，未经作者逐条确认不得成为 confirmed Relation。无法安全匹配已有 RelationType 时必须标为“关系类型待确认”；不得自动创建 RelationType，也不得把叙事相邻静默猜成因果。

当前核心原文：

> 采纳只会通过既有 Event 写入者生成作者草稿，绝不自动进入 Canon；候选关系也不能自动成为正式 Relation。之后是否进入影响审查、确认和 Canon，仍必须走独立、显式的作者确认链。

当前体验路径原文：

> 1. 作者选择一个节点或连续片段。
> 2. 右侧天意 Agent 给出至少一个有依据的虚线后续。
> 3. 作者直接修改、接受、组合或拒绝。
> 4. 被接受内容成为候选节点。
> 5. 作者确认后，候选经过影响审查和唯一正式写入链，写入当前明确的目标故事、事件来源和版本，并保留可追溯记录。

这两段与 Founder 本轮“采纳即最终决定”的新决定存在待写回冲突，请重点评审如何统一术语和状态流。

### 6. 分支感知上下文与注意力隔离

来源：`TIANYAN_PRODUCT_CORE.md`「十一、上下文、记忆与知识边界」。

> 上下文不是左侧侧边栏。左侧侧边栏是工程目录。右侧天意 Agent 是操作界面。上下文是 AI 的参考范围，三者不能混为一个概念。

每个重要 AI 操作应可查看：使用了什么、为何使用、来源版本、排除内容、是否过期、token/预算限制、是否越过角色知识边界、输出影响哪些对象。

每次重要 AI 操作的注意力范围必须同时识别：

- 当前故事或事件来源；
- 当前分支与版本；
- 选中的单元、事件、Agent 或其他筛选范围；
- 本次启用的候选、预测或女娲结果；
- 作者允许的目标写入位置；
- 明确排除的其他分支、版本和结果。

> IF、翻译、改编、不同视角、女娲候选和主故事事实不得静默串线。跨来源内容只有在被明确引用时才可作为只读参考；它不因为被模型看到，就变成当前分支的事实。

> 来源版本、筛选范围、启用结果或目标写入位置发生变化时，已有上下文回执应被标记为过期并重新校验。作者应能看到本次包含了什么、排除了什么以及原因。

### 7. 副本与版本管理

来源：`TIANYAN_PRODUCT_CORE.md`「十四、副本与版本管理」。

统一管理范围包括原始主线、女娲/翻译/视角/IF/本土化改编/手动副本、临时分支、旧版本、单元版本、同步状态、冲突、融入记录、删除与恢复。

> 天衍适合采用类似 Git 的版本思想：每次重要变化有稳定版本；历史可追溯；可以比较；可以恢复；可以分出副本和分支；可以把选择的变化融入目标版本。
>
> 但用户界面不需要强迫普通作者理解 commit、rebase、cherry-pick 等代码术语。产品应使用“版本、同步、对照、融入、恢复”等作者容易理解的语言。
>
> 底层可以内嵌版本库，也可以支持把作品作为可移植工程导出；无论技术实现如何，故事语义不能只依赖 Git 文件差异。

> 旧版本默认保留。除非作者明确永久删除，否则覆盖、同步和融入都不能抹掉历史。

对照需支持事件线叠加、左右分屏、变更列表、单元摘要、Agent/关系/地图/时间差异，并能从差异查看故事语义影响。

### 9. 完整体验与最终产品原则

来源：`TIANYAN_PRODUCT_CORE.md`「十八、完整作者体验」「十九、完整产品的质量要求」「二十、未来 Agent 阅读本文后必须理解的十件事」。

关键路径：

- 只有一个想法：创意对话 → 提炼候选 → 作者审查 → 候选节点 → 作者确认/修改。
- 事件线预测：明确局部范围 → 有据候选 → 作者修改/接受/组合/拒绝 → 候选节点 → 影响审查与唯一正式写入链。
- 女娲深入推演：明确来源/版本/范围/权限 → 有界 Run 或派生副本 → 对照差异 → 选择内容融入 → 新目标版本，旧版本保留。
- 多元派生：选择来源版本 → 建立派生副本 → 作者手动同步并处理冲突 → 默认不反向覆盖来源。

必须成立的质量原则：

- 原始主线与派生副本不互相污染；
- 所有重要结论可追溯到来源或作者决定；
- 能说明上下文、推断与修改影响；
- 重要操作有版本且可撤销；
- 同步不会抹掉历史；
- 外部失败不破坏故事数据；
- 密钥与作品数据分离、外部调用显式、日志不泄露正文和密钥；
- 保持唯一 Canon 写入者、World 事实所有者与 Event 投影/写入边界；
- Pi Agent、Provider、Skill、插件都不能拥有 Canon、Event、WorldState、来源/版本身份、权限或作者确认权。

## Founder 本轮最新决定（高于旧核心表述）

以下是**待写回核心文档的新 Founder 决定**：

### 三种模式

- 创意模式：只存在于天意大页面。
- 工作模式：同时存在于天意大页面和侧边天意。
- Agent 模式：只存在于侧边天意。
- Agent 模式只在支持专属能力的特定页面开放。
- 不同页面打开的 Agent 模式具有不同对象、工具、上下文和专属功能。
- Claude 是顾问，不是编码者；是否调用依据问题价值判断，不制定僵硬规则。

仍待评审，不是已确认事实：

- 天意大页与侧边天意的工作模式是否为同一个可移动会话；
- 创意与工作具体共享/隔离哪些状态；
- Agent Run 如何把摘要与回执送回工作会话而不污染创意对话。

### “采纳”的语义

- 作者主动点击“采纳”，基本上已经作出最终决定。
- 不能对同一个决定反复要求确认。
- 安全与可回溯不能依赖重复弹窗。
- 如果只生成草稿或保留候选，就不应命名为“采纳”。

待评审方案：采纳前展示影响、目标故事、目标版本与变化范围；点击“采纳”即执行一次正式、原子的作者操作；完成后产生新版本、变化回执和撤销入口；只有目标版本过期、实际范围改变或出现新冲突时，才重新请求作者决定。

### 版本与 IF

待评审方案：

- 每次重要采纳产生一个不可混淆的新故事版本；
- 旧版本默认保留，不被覆盖；
- 撤销采纳通过创建反向版本完成，而不是删除历史；
- 未选候选先进入轻量“可能性”区域；
- 重要可能性可由作者升级为长期 IF 线；
- 不为每个 AI 候选自动建立正式分支；
- 可能性与 IF 必须绑定来源故事、基础版本、上下文和生成依据；
- 早期版本产生的可能性必须标记“基于旧版本”，不得被 AI 静默当作当前事实。
