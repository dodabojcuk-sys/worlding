## 一、Claude 最重要的三个新观点

### 1. Agent 回执不能自动成为下一次采纳的上下文

Claude 找到本轮最有价值的遗漏：风险不只是 Agent 内容污染创意对话，而是 Agent 的自然语言摘要被工作会话吸收后，作为“影响说明”间接推动 Canon 写入。这样 AI 虽未直接写入，却事实上成为决定依据的第二 Owner。

最终推荐：Agent Run 的结构化 Candidate/ChangeSet、来源版本、作用范围与工具参数快照可以进入工作会话；自然语言摘要和回执只能作为带谱系的引用展示。采纳预览必须从结构化故事语义 diff 重新生成，不能从摘要复制。

### 2. “创意/工作/Agent”不是一个平面上的三兄弟

Claude 与 Codex 独立判断一致：创意/工作描述作者意图，Agent 描述执行者或执行状态。Claude进一步给出“意图 × 表面 × 执行者”模型：

- 意图：创意 / 工作
- 表面：天意大页 / 侧边天意
- 执行者：作者 / 页面 Agent

Founder 已确认的 R0 只是这个模型中的有效组合，不必为了数学上的全矩阵开放“创意+Agent”或“大页 Agent”。

### 3. 回执必须快照工具参数，过期基座应拒绝而非再确认

页面工具参数可以是表面隔离的瞬时输入，但 Run/采纳回执必须记录实际使用参数、基础版本、范围、来源和对象。采纳使用乐观版本校验；基础版本过期、实际范围改变或出现新冲突时，原操作拒绝提交，作者面对的是新的决定，而不是对旧决定重复确认。

## 三、Codex 接受、调整和拒绝的建议

### 接受

- 采纳预览只从结构化语义 diff 重建，AI 摘要不进入决定链。
- 大页工作与侧栏工作引用同一 Work Session，是同一工作会话的两种表面。
- 共享持久工作状态，隔离未发送草稿、滚动位置、悬停、页面选择和工具输入态。
- 采纳前内联展示目标故事、基础版本、范围、影响与冲突；单击采纳就是唯一作者决定。
- 采纳采用基础版本校验、幂等操作 ID 和全有或全无的作者可见语义。
- 撤销创建补偿版本；恢复旧版本创建新的当前版本；旧历史不删除。
- 工具参数虽是局部输入态，但执行回执必须快照实际参数。
- “重要可能性”必须由作者显式升级，不能由 AI 阈值静默决定。

### 调整

- Claude 的“三轴”适合作为内部产品模型；用户界面仍遵守 Founder 已冻结的三种入口，不在 R0 增加空组合。
- Claude 截断长答曾倾向把创意与工作做成独立会话；Codex 不采用两个互不相干的 Tianyi Session。更稳妥的是同一个 `TianyiConversation` 下的 Creative / Work 两条模式泳道：统一历史可见、来源与候选可追溯，但上下文装配和瞬时工作状态按泳道隔离。
- Agent 的结构化结果可以进入 Work Session 的候选池；被隔离的是未经验证的自然语言结论，不是所有 Agent 产物。
- 不明 RelationType 默认阻断包含它的采纳；作者可先明确缩小范围，将关系留为独立候选，再采纳剩余完整变化。
- “可能性”不是自动永久，也不是几轮后不可恢复地删除：未主动保留的候选短期可恢复；作者主动保留后跨会话持久；升级 IF 后获得派生副本身份与版本链。

### 拒绝

- 拒绝把“AI 永不写 Canon”写成绝对产品规则。正确规则是 AI 不拥有 Canon，不可绕过作者权限和唯一 Owner；明确授权后的工具执行仍可由 AI 发起，由领域写入者提交。
- 拒绝把“从 IF 部分融入后，IF 自身剩余部分自动改变”为默认语义。融入应在目标故事创建新版本；IF 原版本保持不变，只新增“哪些变化已被某目标融入”的回执投影。
- 拒绝因为 Agent 是逻辑执行轴，就在本轮开放大页 Agent 或创意 Agent；这会扩大 Founder 已冻结范围。

## 四、当前最合理的产品模型

### 1. 模式与页面

| 有效组合 | 会话身份 | 主要职责 |
| --- | --- | --- |
| 天意大页 · 创意 · 作者 | `TianyiConversation / Creative lane` | 发散对话、原话保留、提炼故事种子 |
| 天意大页 · 工作 · 作者 | `TianyiConversation / Work lane` | 深度分析、方案发展、候选与采纳 |
| 侧边天意 · 工作 · 作者 | 同一 `Work lane` 的页面投影 | 围绕当前页面继续同一工作 |
| 侧边天意 · Agent | Page-scoped Run，无独立会话 Owner | 用当前页对象、工具、范围执行委派任务 |

整个 `TianyiConversation` 共享：统一可见的历史谱系、来源、附件、显式引用与候选注册表。每条消息、候选和回执都保留所属泳道、来源与基础版本，不能因为“全局可见”就自动进入另一泳道的 ContextPack。

大页与侧栏的 Work lane 进一步共享：工作消息流、目标故事、基础版本、审查状态、Run 索引与回执。

泳道隔离：创意草稿/探索范围与工作草稿/任务范围/审查进度互不污染；跨泳道内容只有显式引用时进入本次上下文。

表面隔离：未发送草稿、光标、滚动、展开状态、临时选择、局部筛选、工具输入参数和布局。工具一旦执行，其实际参数进入 Run 回执。模式切换不清空任何泳道，也不丢失统一会话历史。

### 2. Agent 回流合同

```text
Page Agent Run
  → Structured Candidate / ChangeSet
  → Source + BaseVersion + Scope + ToolParameterSnapshot
  → ReceiptRef + Human-readable Summary
  → 显式挂入 Work Session 候选池
```

自然语言 Summary 只展示；不进入采纳 diff、不自动进入长期记忆，也不因被模型看到而成为当前故事事实。

### 3. 采纳状态流

```text
候选
  → 补全目标故事 / 基础版本 / 范围 / 关系类型
  → 从结构化故事语义 diff 生成影响预览
  → 作者单击“采纳”
  → 校验基础版本、范围、新冲突和幂等键
  → 唯一 Owner 协调原子提交
  → 新故事版本 + 回执 + 撤销入口
```

校验失败时不产生半版本；返回“目标已变化/范围已变化/出现新冲突”，要求基于新事实重新决定。高影响只改变采纳前信息密度和必填条件，不增加第二次确认。

### 4. 版本、可能性与 IF

| 对象 | 是否故事事实 | 是否有稳定版本身份 | 生命周期 |
| --- | --- | --- | --- |
| 候选 | 否 | 候选 ID | 短期、可恢复 |
| 工作草稿 | 否 | Work Session 内身份 | 表面/会话 |
| 已保留可能性 | 否 | 来源决策点 + BaseVersion | 跨会话持久、只读惰性 |
| 临时分支 | 否，除非在派生副本内授权有效 | 临时身份 | 可比较、放弃或升级 |
| 长期 IF | 在自身副本内有效 | 派生副本 + 独立版本链 | 长期 |
| 已采纳版本 | 当前目标故事事实 | 稳定版本 ID | 永久 |
| 历史版本 | 旧的正式状态 | 稳定版本 ID | 永久只读 |
| 待合并变化 | 否 | ChangeSet ID | 到融入/拒绝/归档为止 |

四个动作：

- 撤销：在当前目标上创建补偿版本。
- 恢复：以旧快照内容创建新的当前版本。
- 从旧版本创建 IF：创建锚定旧 BaseVersion 的新派生身份。
- 从 IF 部分融入：生成绑定 IF 来源版本与当前目标版本的语义 ChangeSet；采纳后只改变目标故事，IF 保持原历史并增加融入回执。

故事差异必须覆盖 Event、Relation、Canon、WorldState、Agent 状态、知识/记忆边界和叙事编排；文本或文件 diff 只作证据与表现补充。

## 五、真正需要 Founder 决定的问题

1. **是否冻结 Tianyi 会话拓扑：一个统一会话、Creative/Work 两条泳道，Work 在大页与侧栏共用？**
   推荐：是。统一历史、来源与候选可见；上下文装配和瞬时状态按泳道/表面隔离。这既延续“同一段天意会话”，又避免工作回执污染创意推理。

2. **R0 是否明确锁定单作者/单活动写入者？**
   推荐：是。R0 使用基础版本过期即拒绝，不实现多人合并；未来协作再设计显式合并，不用 last-write-wins。

3. **未主动保留的候选采用什么保留期？**
   推荐：产品语义先冻结为“短期、可恢复、可批量清理”，不在核心写死具体天数；作者点击“保留可能性”后跨会话持久，点击“升级 IF”后建立派生副本。

## 六、与上一轮评审的关系

上一轮 Claude 已提出三个基础结论：候选到已确认应为原子、可见、带回执且可撤销的作者动作；创意/工作共享可追溯材料但隔离瞬时状态；摘要必须版本化且不覆盖原文。

本轮没有推翻这些结论，真正新增并改变判断的是：

1. Agent 摘要必须从采纳决定链中物理隔离，影响预览由结构化语义 diff 重建。
2. 工作大页与侧栏应是同一 Work Session 的两种表面，而不是两套相似对话。
3. 回执不仅记录结果，还必须快照工具参数、基础版本与作用范围。
4. 单击采纳的安全依赖前置完整性和版本校验，而不是重复确认。
5. “可能性”需要显式保留门和可恢复清理策略，不能把分支爆炸换成永久元数据垃圾。

## 七、本轮已写回核心文档的冲突

1. 天意大页“创意模式 / 对话模式”已改为“创意模式 / 工作模式”。
2. 侧栏“对话 / Agent”已改为“工作 / Agent”，并明确工作是同一 Work lane 的页面投影。
3. “采纳只生成作者草稿，之后再影响审查、确认和 Canon”已拆分：生成草稿/保留候选不叫采纳；影响审查在采纳前；采纳本身是一次正式、原子、可撤销的作者决定。
4. 已补写 Agent 回执与摘要的上下文地位：结构化候选可显式挂入工作候选池；自然语言摘要不能自动成为采纳依据或正式记忆。
5. 已补写版本与可能性的生命周期：旧版本永久保留；普通候选短期可恢复；作者保留的可能性跨会话持久；长期 IF 是派生副本。

## 八、Founder 正式确认与核心写回状态

Founder 已正式确认：一个 `TianyiConversation` 与 Creative / Work 两条泳道；大页“创意 / 工作”；侧栏“工作 / Agent”；同一 Work lane 的两种表面；Agent 为 Page-scoped Run；R0 单作者与同目标唯一正式写入者；一次采纳、新版本、结构化回执和补偿版本；候选历史不静默永久删除；保留可能性跨会话持久；升级 IF 才建立派生副本。

## 九、当前隔离原型下一轮必须修复的差异

1. 原型仍使用“确认采纳并创建草稿”和“采纳后只创建模拟草稿”的旧语义。下一轮必须拆分“保存草稿 / 保留候选 / 保留可能性 / 升级 IF / 正式采纳”，正式采纳直接生成目标新版本、结构化回执与补偿撤销入口。
2. 原型影响审查尚未表达 `BaseVersion`、明确目标、结构化故事语义 diff、对象级追溯、安全工具参数快照及版本过期拒绝。
3. 原型与相关目录表达中的“已分类 / 待确认”问题仍混合分类状态和权威确认状态。下一轮必须把“已分类 / 未归类”和“候选 / 待确认 / 已确认”设计为正交维度；本轮不修改 UI。
4. 原型虽然保留统一会话历史，但尚未给消息、候选和回执标注 Creative / Work 泳道，也未证明跨泳道 ContextPack 显式引用；侧边 Work lane 与 Page-scoped Agent Run 也尚未成为该 fixture 的完整状态。
